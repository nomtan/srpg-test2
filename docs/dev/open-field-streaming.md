# Open Field — 大規模マップ対応 (チャンクストリーミング)

`samples/JRPGWorldSample2.tscn` (`scripts/world_jrpg/open_field_world.gd`) の地形・木・岩・低木・草を、
全域一括生成から **32m区画 (CHUNK) 単位のストリーミング** に切り替えた。見た目の規則 (高さ・バイオーム・植生の
密度・LOD・草の距離制御・影の距離) は従来のまま。

| ファイル | 役割 |
|---|---|
| `scripts/world_jrpg/open_field_chunks.gd` | 区画の状態・目標レベル・解放・優先度キュー・ワーカースレッド・フレーム予算・固定範囲 (新規) |
| `scripts/world_jrpg/open_field_world.gd` | 区画単位の生成 (`_tile_*_task`)、メインスレッドでのノード化 (`_*_steps`)、遠景ブロック |
| `scripts/world_jrpg/open_field_biome.gd` | 区画ごとのバイオーム窓 `Patch`、シェーダー用マップの区画単位書き込み |
| `scripts/world_jrpg/open_field_vegetation.gd` | 遠景の森用 `add_far_trees` (最遠LODのみ・影なし) |
| `scripts/world_jrpg/verify_streaming.gd` | 検証 (下記) |
| `scripts/world_jrpg/bench_open_field.gd` | 起動時間・メモリ・フレーム時間の計測 (新旧どちらの実装でも動く) |

`castle_city_world.gd` (JRPGWorldSample3) は従来どおり全域配列 (dense) で動く。共通関数は `streamed` で分岐する。

## 構成

### 区画レベル

区画は距離 (探索者・その予測位置・カメラから区画の正方形まで) に応じて段階的に上げ下げする。
読み込み距離と解放距離 (`+ release_margin`) を分けているので、境界の往復で生成と解放を繰り返さない。

| レベル | 内容 | 既定の読み込み距離 |
|---|---|---|
| PLAN | 高さ・バイオーム・水・道路を一度計算し、木と岩を配置 (計画)。密データは捨ててよく、計画は遠景の森に使う | `far_radius` 512m |
| DATA | 密データ (高さ・バイオーム・水位・道路距離の窓) を保持。当たり判定・地形APIはここを読む | `data_radius` 256m |
| TERRAIN | 1m地形メッシュ (外側は遠景ブロックの8m格子) | `terrain_radius` 224m |
| DETAIL | 木のLOD階層・岩・低木 (外側は遠景の森) | `detail_radius` 128m |
| GRASS | 草のカーペットと花 | `grass_radius` 96m |

草 (FAR_END 76m)・低木 (120m)・木のLOD (seed木はLOD2が100mから、他はLOD3が120mから無影) の描画距離は
各読み込み距離の内側で終わるので、カメラから見える範囲の描画内容は一括生成と同じになる。

### 区画データ (`_tile_data_task`)

- 各区画は周囲 `APRON` (2点) 分を含む 37×37 点の窓を持つ: ゲームプレイ高さ `gh`、見た目の高さ `vh`
  (+マイクロ起伏)、水位、道路までの距離。バイオームは 2m 格子の 19×19 点 (`Biomes.Patch`)。
- 区画の生成処理が読む点 (双一次補間・±0.5m の勾配・±1m の法線・2m のバイオーム) はすべて自分の窓に収まる。
- 値はすべて「位置とシードだけの純関数」。隣接区画の窓の重なりは完全に同じ値になるので、境界の頂点・法線は
  ビット単位で一致する (検証済み)。
- 川・道路は全域ラスタをやめ、線分を区画ごとのバケットに分けて点ごとに問い合わせる (`_river_hit` / `_path_query`)。
- 木・岩・低木・草は区画 (草は区画内の約10m小区画) ごとに `hash(シード, 区画座標)` で初期化した乱数で配置する。
  読み込み順序や回数に関係なく同じ配置になる。

### スレッドと分散

- 生成は `WorkerThreadPool` のタスク。読むのはワールドの固定レイアウト (地形定義・川・道路・ランドマークの障害物)
  と自分の区画 (と隣接区画の木の矩形) だけ。
- メインスレッドは完成した結果を小さなステップ (地形メッシュ / 木 / 低木 / 草の小区画ごと) でノード化し、
  1フレームあたり `stream_budget_ms` まで実行する (最低1ステップ)。
- 優先度は距離順。計画リング (大きなマップでは千区画以上) の再判定は数行ずつ複数フレームに分ける。
- 同時タスク数は最大4。GDScriptのメソッド呼び出しはスレッド間でエンジン内部の競合があり、4本で単スレッドの約2倍、
  8本以上では逆に遅くなる (計測値)。同じ理由で、ホットパスが読む設計定数は入れ子配列ではなく Packed 配列にしてある
  (`mesa_rows` など)。

### 遠景

- **遠景ブロック**: 4×4区画 (128m) ごとに 8m 格子の地形メッシュ。1m地形のある区画を除いたインデックスを組み直し、
  境界には両面のスカートを下げて隙間を塞ぐ (1m地形側にもスカートあり)。
- **遠景の森**: 同じブロック単位で、計画済み・詳細未表示の区画の木を最遠LODだけの MultiMesh (影なし) で描く。
- フィールド外周の山並み・海・湖・川・崖・城や町などのランドマークは従来どおり起動時に一度だけ作る
  (ランドマークが立つ区画は起動時に並列で先読みする)。
- 区画の詳細を外すときは、先に遠景ブロック / 遠景の森をその区画を含む形で作り直してからノードを解放するので、
  穴が1フレームも開かない。

### 先読み・当たり判定

- 中心は探索者・`stream_lookahead` 秒先の予測位置・カメラ。近い区画から順に生成する。
- `_can_walk` は、移動先の区画とその8近傍に高さと障害物 (幹・岩) がそろっていなければ移動を拒否する
  (未生成区画への侵入・落下の防止。発生回数は `chunks.counters.stalls`)。通常は先読みで 0 回。
- 地形API (`get_gameplay_height` など) は区画が未生成ならその場で生成して正しい値を返す (`sync_loads`)。

### SRPG戦闘用: 範囲の固定

```gdscript
var id := world.pin_battle_area(Rect2(x, z, w, h))  # 範囲に掛かる区画を GRASS レベルで保持し、解放しない
world.release_battle_area(id)                       # 通常のストリーミングに戻す
```

## 設定項目 (`open_field_world.gd` の Streaming グループ)

| 項目 | 既定 | 内容 |
|---|---|---|
| `field_size` | 400 | 歩けるフィールドの一辺 (m)。設計された地形は 0–400m、それより外は外周の丘・海岸・海がそのまま続く |
| `grass_radius` / `detail_radius` / `terrain_radius` / `data_radius` / `far_radius` | 96 / 128 / 224 / 256 / 512 | 各レベルの読み込み距離 (m) |
| `release_margin` | 32 | 解放は読み込み距離 + この距離を越えてから |
| `stream_lookahead` | 1.2 | 予測位置の先読み秒数 |
| `stream_budget_ms` | 3.0 | メインスレッドでのノード化に使う 1フレームの時間 |
| `stream_jobs` | 0 | 同時生成タスク数 (0 = CPUスレッド数の1/4、1–4) |
| `startup_radius` | 128 | 起動時にこの距離までは読み込みを終えてから開始 |

コマンドライン: `--field-size=<m>`、`--stream=<grass>,<detail>,<terrain>,<data>,<far>`、`--stream-margin=<m>`、
`--stream-jobs=<n>`、`--stream-budget=<ms>`、`--startup-radius=<m>`。F4 の地形情報パネルに区画数を表示する。

## 検証

```bash
# 区画数の上限・往復時の再現性・読み込み順序・境界・当たり判定・固定範囲 (headless)
godot --headless --path . -s res://scripts/world_jrpg/verify_streaming.gd
godot --headless --path . -s res://scripts/world_jrpg/verify_streaming.gd -- --field-size=1600
# 起動時間・メモリ・フレーム時間 (ウィンドウ、vsync OFF、16 m/s でルート走行)
godot --path . --resolution 1920x1080 -s res://scripts/world_jrpg/bench_open_field.gd -- --out=<file.json>
godot --path . --resolution 1920x1080 -s res://scripts/world_jrpg/bench_open_field.gd -- --field-size=1600 --route=east
```

`verify_streaming.gd` は読み込み距離を小さくして (草40 / 詳細64 / 地形80 / データ96 / 計画160m) 往復ルートを走り、
区画の解放と再生成を数百回起こしてから確認する。

### 観察した停止

- 走行中に 500ms 前後の停止が数回出ることがあった。停止したフレームではストリーミング側の処理が何も動いておらず、
  全区画を事前に読み込んで走行中のストリーミングを止めても同じ場所で再現した (旧版も1回目の実行で出る)。
  描画側 (パイプライン生成など) によるもので、この改修の範囲外。
- ストリーミング自身のメインスレッド処理は1フレーム最大 6–14 ms (400m)、1600m で最大 30 ms 程度
  (`chunks.counters.max_frame_ms`)。

## 既知の制約・今後

- **木・岩・低木・草の個々の配置**は旧版と異なる (区画単位の乱数にしたため。密度・分布の規則は同じ)。
- **スレッド数**: GDScript の多スレッド実行はエンジン内部で競合し、4本以上で頭打ち。区画データ生成 (約40ms/区画) を
  さらに速くするには、地形関数の静的関数化や GDExtension 化が必要。
- **遠景の森**は計画 (= 高さ・バイオームの計算) が済んだ区画しか描けない。大きなマップを全力で走り続けると、
  500m 先の計画リングが数秒遅れて埋まる (起動直後の `settle` も同じ理由)。
- 城・町・村・遺跡・湖・海・川・崖・外周の山並みは起動時に一度だけ作る固定物のまま。
- `--dump-maps` は全区画を生成するため、大きなマップでは時間がかかる。
